TAREFA 1 - Bug intermitente de CSS, local e produção (B11)
----------------------------------------------------------------------
Sintoma: às vezes o site fica sem CSS. Algumas páginas aparecem estilizadas e outras não.

Importante: isso acontece também no localhost (npm run dev). Então a causa está no código ou na configuração do projeto, não na Vercel. Depure primeiro localmente. As causas que só existem em produção (cache, rewrites, CSP, configuração do projeto na Vercel) ficam para o final e só entram se o bug continuar no site publicado.

Diagnóstico (faça ANTES de mudar código):
1. No localhost, abra uma rota que falha e inspecione um elemento sem estilo (DevTools, aba Elements). Veja se a classe está no elemento mas sem nenhuma regra CSS aplicada (o Tailwind não gerou a classe) ou se a folha de estilo inteira não carregou (aba Network, filtro CSS).
2. Na aba Network, confira se o CSS principal é pedido nessa rota, com status 200 e content-type text/css.
3. Olhe o terminal do "npm run dev" e o Console do navegador: erros do Tailwind ou do PostCSS, "Failed to resolve import", "Failed to fetch dynamically imported module", erros de CSS e o overlay de erro do Vite.
4. Anote quando acontece: na primeira carga, ao navegar entre páginas sem recarregar, depois de Ctrl+Shift+R ou depois de salvar um arquivo (HMR). Teste também se o problema some ao apagar a pasta node_modules/.vite e reiniciar o servidor.
5. Compare "npm run dev" com "npm run build && npm run preview". Falhando nos dois: configuração ou estrutura dos imports de CSS. Falhando só no preview: remoção de classes (purge), minificação ou divisão em chunks.

Causas prováveis (confirme cada uma antes de corrigir):
C1. Os caminhos de content do Tailwind não cobrem todas as pastas que usam classes (src/components/ui, src/pages, index.html...). Classes usadas só em arquivos não cobertos nunca são geradas, e por isso só algumas páginas ficam quebradas. Confira o tailwind.config (v3) ou a detecção de fontes (v4) e o components.json.
C2. CSS global importado no lugar errado: o index.css (com as diretivas ou o import do Tailwind) deve ser importado uma única vez, em src/main.tsx, nunca dentro de uma página ou de um componente carregado sob demanda. Remova restos do template do Vite (App.css, index.css duplicado) e garanta uma única configuração de Tailwind (sem misturar v3 e v4, sem tailwind.config junto com um @theme conflitante).
C3. CSS importado por componentes de rota ou por chunks carregados sob demanda (import './Pagina.css'): a ordem de carregamento muda com a navegação, então regras de uma página sobrescrevem ou vazam para outra, e um chunk que falha leva embora o estilo daquela página. Mova as regras compartilhadas para o arquivo global ou para classes do Tailwind e evite CSS de página sem escopo.
C4. URLs relativas de CSS ou de arquivos (<link href="styles.css">, url(imagens/x.png) no CSS, arquivos de public/ citados sem a barra inicial) quebram em rotas aninhadas como /my-submissions/123, no dev e em produção. Use caminhos absolutos começando com "/" e base '/' no vite.config.
C5. Classes montadas dinamicamente (ex.: bg-${cor}-500) nunca são geradas pelo Tailwind, nem classes que vêm do banco de dados. Use nomes de classe completos e literais ou um mapa de correspondência.
C6. Problemas de PostCSS ou de Vite: postcss.config ausente ou com nome errado, plugin errado (@tailwindcss/vite x plugin do PostCSS), configurações duplicadas (.js e .cjs), cache velho em node_modules/.vite.
C7. Configuração do shadcn/ui: o caminho de css no components.json aponta para um arquivo diferente do que é importado, variáveis CSS (--background, --foreground, --primary...) ausentes em :root, ou a classe dark alternando de forma inconsistente, o que faz alguns componentes aparecerem sem cor.
C8. Nomes de arquivo com espaço, acento ou maiúsculas diferentes entre o import e o arquivo real (Logo.png x logo.png). Funciona no Windows e no macOS e falha no build Linux. Use nomes em minúsculas, sem acento, em kebab-case.
C9. Só em produção, confira por último: index.html antigo apontando para arquivos com hash que não existem mais depois de um deploy; fallback de SPA devolvendo index.html para um arquivo que não existe (CSS servido como text/html); CSP do S08 bloqueando estilos inline usados pelo shadcn/Radix; configuração do projeto na Vercel (Framework Preset "Vite", build "npm run build", output "dist", versão do Node em package.json engines, package-lock.json commitado). A configuração da Vercel é feita no painel, então documente no README.

Reforço para produção (só depois de corrigir a causa local, e só se o site publicado ainda falhar):
- Cache-Control "no-cache" para index.html e "public, max-age=31536000, immutable" para /assets/*.
- Listener do evento 'vite:preloadError' que recarrega a página uma única vez.
- vercel.json: /assets/* nunca é reescrito, e o fallback de SPA vale só para caminhos que não são arquivos.
- CSP: permitir 'unsafe-inline' apenas em style-src. Nunca afrouxe script-src.

Se não achar a causa, pare e relate em vez de adivinhar: quais rotas falham, as evidências do DevTools (Elements e Network), os arquivos de configuração do Tailwind, PostCSS e Vite, o src/main.tsx e o index.css.

Critérios de aceite:
- Com "npm run dev", toda rota aparece totalmente estilizada na primeira carga, ao navegar entre todas as rotas e ao recarregar à força um link direto.
- O mesmo resultado com "npm run build && npm run preview" e no site publicado.
- Sem erros de CSS, Tailwind ou PostCSS no terminal e no Console, e sem erros 404, de MIME ou de CSP na aba Network em /login e /campaigns.
- Um teste de fumaça ou uma lista de conferência manual que visite todas as rotas.
- A causa raiz confirmada está escrita na descrição do PR e em docs/CHANGELOG.md. Não aplique correções para causas que não foram observadas.

TAREFA 2 - Redefinir senha (B12)
----------------------------------------------------------------------
Hoje o usuário que esquece a senha não tem como recuperá-la.

Use somente o que o Supabase já oferece (R01, R02): supabase.auth.resetPasswordForEmail e supabase.auth.updateUser. Nada de token próprio.

Rotas novas (públicas): /forgot-password e /reset-password.

Fluxo:
1. Na tela /login, adicione o link "Esqueci minha senha" apontando para /forgot-password.
2. /forgot-password: formulário com e-mail e captcha (Turnstile, igual ao login). Chame
   supabase.auth.resetPasswordForEmail(email, { redirectTo: window.location.origin + '/reset-password', captchaToken })
   Mostre SEMPRE a mesma mensagem, exista ou não o e-mail: "Se o e-mail estiver cadastrado, você receberá um link para redefinir a senha." (S09, sem enumeração de usuários). Desabilite o botão por 60 segundos após o envio.
3. O e-mail leva o usuário a /reset-password. A página deve escutar supabase.auth.onAuthStateChange e reagir ao evento 'PASSWORD_RECOVERY' (e também checar se já existe sessão de recuperação). Sem sessão de recuperação, mostre "Link inválido ou expirado" com botão para /forgot-password e NÃO chame updateUser.
4. Formulário com nova senha e confirmação, validado com zod: mínimo de 10 caracteres (auth_rules.password_min_length) e confirmação igual. Chame supabase.auth.updateUser({ password }). Em caso de sucesso, chame supabase.auth.signOut(), mostre um aviso de sucesso e redirecione para /login.
5. RouteGuard: /forgot-password e /reset-password devem abrir para qualquer usuário, inclusive pending e rejected, e um usuário em sessão de recuperação não pode ser redirecionado antes de trocar a senha.
6. Nunca registre em log o e-mail nem tokens (R09). Não leia o token da URL manualmente: o supabase-js já faz isso.

Testes (vitest + testing-library):
- Mesma mensagem para e-mail cadastrado e não cadastrado.
- /reset-password sem sessão de recuperação mostra "link inválido" e não chama updateUser.
- Senha com menos de 10 caracteres ou confirmação diferente é recusada.
- Após trocar a senha, o usuário é deslogado e vai para /login.
- Usuários pending e rejected conseguem abrir as duas rotas.

Critérios de aceite: fluxo completo funcionando (pedir link, abrir o e-mail, trocar a senha, entrar com a nova), testes passando, passos manuais documentados no README.

- Referência visual: o arquivo img/EMBLEMA VIRTUDES ATEMPORAIS.png é a referência de todo o rebranding. Abra a imagem antes de qualquer trabalho de design: cores, clima e formalidade das telas devem seguir o que está nela. Não mova, renomeie, edite nem apague esse arquivo; ele fica em img/.
- Emblema: copie img/EMBLEMA VIRTUDES ATEMPORAIS.png para src/assets/brand/emblema-virtudes-atemporais.png (a cópia é renomeada, sem espaços nem maiúsculas, ver causa C8; o app importa só a cópia, nunca o arquivo de img/). - Contraste: pares texto/fundo precisam passar WCAG AA (4,5:1 para texto normal e 3:1 para texto grande). O dourado costuma falhar como texto sobre branco. Use o dourado em bordas, ícones, badges, divisores e títulos grandes sobre azul escuro, e o azul escuro para texto e botões.

Direção visual (vale para B14 a B16): moderna e limpa.
- Espaçamento em múltiplos de 8 px, container com largura máxima, bordas arredondadas (rounded-lg), sombras suaves, sem gradientes pesados.
